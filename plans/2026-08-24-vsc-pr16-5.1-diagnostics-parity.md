# Parity plan: VS Code extension v5-1-0-support (PR #16) → SwiftUI + Android

**Status:** Ready for implementation
**Source PR:** [getditto/vsc-es#16](https://github.com/getditto/vsc-es/pull/16) — "Ditto SDK 5.1: production diagnostics — debug socket console, system:metrics, ADVISE, log patterns" (commit `84afa4b`, local branch `v5-1-0-support` in `~/Developer/ditto-vsc-es`).
**Goal:** make the SwiftUI app and the Android app match the four capabilities that PR added to the VS Code extension.

## What PR #16 ships (evidence trail)

### A. Debug Console (`debug_socket`, SDK 5.1)

An app sets `ALTER SYSTEM SET debug_socket = '<path>'` at runtime and Ditto spawns an
**unauthenticated newline-delimited DQL listener** on a Unix domain socket
(`crates/ditto-configuration/src/index.json` — `debug_socket`; "fully runtime-configurable",
empty string tears the socket down).

Extension implementation (files: `src/ditto/DebugSocketClient.ts`,
`src/panels/DebugConsolePanel.ts`, `webview-ui/debugConsole/`):

- Standalone panel (`Ditto: Open Debug Console`) — intentionally does **not** require an
  extension-side Ditto connection; it diagnoses processes you don't control.
- Protocol: one DQL statement per line → one reply line (JSON array of items, or
  `ERROR: <message>`). Persistent multi-query connection; requests FIFO-paired (no request
  IDs on the wire); 30 s timeout fails the queue; 64 MiB response-line cap; ≤10 in-flight;
  host-side 10k row cap mirroring `MAX_QUERY_ROWS`.
- Panel shows a **live-mutation warning** — `dql_enable_remote_full_syntax` defaults to
  true in 5.1, so `EVICT`/`ALTER SYSTEM` genuinely work over the socket.
- 34 tests incl. real `net.createServer` client↔server round-trips.

### B. `system:metrics` in the Database Metrics panel

(`src/ditto/SystemMetricsService.ts`, `src/panels/DatabaseMetricsPanel.ts`,
`webview-ui/databaseMetrics/`)

Key host-side facts (verified against `crates/ditto-metrics-exporter-virtual-collection/`):

- The exporter is **startup-gated**: `metrics_exporter_virtual_collection_enabled` defaults
  to `false`, and runtime `ALTER SYSTEM` is ignored — "read once at install time". The
  extension flips `DITTO_METRICS_EXPORTER_VIRTUAL_COLLECTION_ENABLED` around `Ditto.open`
  (env vars `DITTO_<UPPER_SNAKE>` map to parameters).
- When the exporter wasn't installed, `SELECT * FROM system:metrics` succeeds but returns a
  placeholder row `{status:"disabled", description:…}` without a `key` — that's the UI's
  "exporter disabled" state.
- **Every scan flushes the registry**: counter rows carry per-read `delta`, histogram rows
  `dcount`/`dsum`/`dabs_max`. The service **accumulates deltas since connect** — last-read
  rendering would collapse to near-zero after the first poll.
- Poll cadence 5 s while the panel is visible; dashboard over the nine
  `ditto.network.dsoq.*` counters with an opened-vs-closed divergence alert.

### C. ADVISE in the Query Editor

(`src/ditto/advise.ts`, `src/panels/QueryEditorPanel.ts`, `webview-ui/query/`)

- Runs `ADVISE <SELECT …>`; result rows carry an `advice` object:
  `{statement, outcome?, suggestedIndexes: [{collection, reason, statement}]}`
  (e.g. `CREATE INDEX IF NOT EXISTS adv_atest_e ON default:\`atest\` (\`e\` ASC)`).
  `suggestedIndexes` may be absent; `outcome` (e.g. "no keys to advise on") explains why.
- Extractor is forward-compatible: scans every row, merges, drops incomplete suggestions.
- Each suggestion gets an **apply-with-confirmation-modal** path (execution of the CREATE
  INDEX statement). `ADVISE AND PROVISION` is deliberately never used (auto-apply of
  unknown DDL is unsafe).
- `EXPLAIN ADVISE …` is invalid syntax, so the EXPLAIN action skips ADVISE queries.

(`src/logAnalyzer/patterns/problem_patterns.json` + fixtures)

| `replication_metadata_corrupt_recovery` | 3 | warn | `session metadata database was corrupt on open; deleting and reinitializing this` |

| `replication_reset_local_trigger` | 3 | warn | `replication reset was triggered by local peer` |
| `post_eviction_cleanup_frequent` | 2 | — | `post-eviction session cleanup is running too frequently, which may cause excessi…` |

Fixture files live in the extension at
`src/logAnalyzer/patterns/__fixtures__/{remediation…}/` with paired `.txt`/`.expected.json`
round-trip tests.

## Current state in this repo

- The log-pattern engine + catalog + management UI already exist on both platforms
  (shipped this month on `release-1.0`) — schema is byte-compatible with the extension's,
  so item D is a file sync + test couplet per platform.
- Query workbench already executes arbitrary DQL and has an Add Index sheet — so ADVISE's
  apply path can reuse `CollectionsRepository.createIndex` *statement execution* on both
  platforms (the suggestions come back as full `CREATE INDEX` statements; run them verbatim
  after confirmation, like the extension does).
- Both apps have an "Advanced Configuration" surface for startup params; neither can flip a
  **startup-gated** parameter today — the Android applier applies via post-open
  `ALTER SYSTEM` (ignored for this param by design); the env-var path needs to be added in
  `DittoManager` before the Ditto instance opens.
- No `system:metrics` / `system:vitals` UI exists anywhere (earlier research confirmed no
  public counters API in 5.1.0 — this virtual-collection exporter is the supported path).
- No Unix-socket client exists on either platform.

## Work items

### Phase 1 — Log pattern catalog sync (trivial; both platforms)

1. Append the 4 new patterns to `SwiftUI/EdgeStudio/Resources/problem_patterns.json` and
   `android/app/src/main/assets/problem_patterns.json` (byte-for-byte from the extension).
2. Port the fixture couplets as unit tests (input line → expected match/non-match) in
   `EdgeStudioUnitTests/Logging` and `app/src/test/.../data/logging/`.
3. Acceptance: full suites green; all 13 catalog patterns validate through
   `LogPatternEngine.rejectReason`.

### Phase 2 — ADVISE (small-medium; both platforms) — **Implemented** (2026-08-29)

SwiftUI:
- `DQLTools`/service: `runAdvise(query)` → parse `advice` object (forgiving extractor mirroring
  `advise.ts`), models `QueryAdvice`/`QueryIndexSuggestion`.
- Query detail UI: "Advise" action in the editor toolbar (only for SELECT); advice card under
  the results with outcome text or suggestion rows (collection, reason, statement) and
  "Apply" per suggestion → confirmation dialog → execute the CREATE INDEX statement.
- `EXPLAIN ADVISE …` skip guard (toolbar EXPLAIN disabled for ADVISE statements).
- Unit tests: extractor (merge/partial/outcome/empty), no-Ditto UI states.

Android:
- `data/repository/` advise execution via `QueryExecutionService`; same extractor in Kotlin.
- Toolbar: "Advise" entry next to "Run EXPLAIN" (gated to SELECT); advice card in the editor
  area; apply-with-confirm dialog → reuses statement execution.
- EXPLAIN action guard.
- Unit tests mirror Swift; toolbar UI tests extended.

### Phase 3 — `system:metrics` observability (medium; both platforms) — **Implemented** (2026-08-29)

1. **Activation**: a `DittoManager` pre-open hook that sets
   `DITTO_METRICS_EXPORTER_VIRTUAL_COLLECTION_ENABLED` when the new Settings toggle
   **"Collect system metrics"** is on — **default ON** (matches the extension). Note
   the trade-off explicitly documented in Settings copy: the toggle flips an env var
   read only at Ditto construction, so its semantics are *"takes effect the next time
   you open a database"*; guiding text goes on the toggle's subtitle. (The until-now
   open question "on or off by default" resolves to *ON* — users who need the
   dashboard won't find it otherwise, and the polling below is visibility-gated so
   the steady-state cost is near zero.)
   - macOS/iOS: `setenv` before Ditto init.
   - Android: `android.system.Os.setenv(name, value, true)` before the Ditto constructor
     runs (verify on the emulator; if the SDK reads env via a different process boundary,
     fall back to documenting the limitation and leaving the section hidden unless present).
2. **Service**: `SystemMetricsService` equivalent per platform — 5 s polling only while the
   dashboard section is visible, delta-accumulating store (counter `delta`; histogram
   `dcount`/`dsum`/`dabs_max`), placeholder-row classification for the exporterDisabled
   state.
3. **Dashboard UI** (layout agreed during review):
   - **SwiftUI home:** App Metrics destination — a new segmented sub-tab (or a section in
     the existing segmented Process/Queries/Storage view) labelled *System Metrics*, with
     help-markdown parity in the inspector.
   - **Android home:** Database Metrics section — a namespace-filter chip row ("all",
     `ditto.network.*`, `ditto.store.*`, `ditto.sync.*`) above a counter table; smartphones
     get a single column, ≥840dp gets two-column cards.
   - **Content (both):** summary cards for queries/peers/syncs/resets ("since connect"
     totals + per-poll rate), the counter table, histograms collapsed behind a
     "Show histograms" expansion, and the `ditto.network.dsoq.*` opened-vs-closed
     divergence alert banner.
4. Unit tests: accumulation semantics (double-flush→totals), placeholder classification,
   label-signature GC behavior (deltas keep accumulating).

### Phase 4 — Debug Console (PoC-gated; scope: our own Ditto only)

**Scope decision (from review):** we only need visibility into **the app's own embedded
Ditto instance** — no generic connect-to-any-socket-path UX, no remote diagnosis of foreign
processes.

**PoC first (no UI until this passes):**

1. Create the socket for our own instance via
   `ALTER SYSTEM SET debug_socket = '<app-private-path>'` at session open when a new
   "Debug console" Advanced-Configuration toggle is on (default OFF; only diagnostics work
   needs it, and the listener is unauthenticated so don't leave it on).
2. macOS spike: `Network.framework` `NWConnection` to a Unix endpoint; confirm newline/DQL
   round-trips against a live embedded listener.
3. Android spike: `android.net.LocalSocket` (filesystem namespace), same round-trip tests on
   the `tabletApi34` managed device.
4. If either platform fails, ship that platform without the console and note the limitation —
   no user should be led into a broken feature.

**Console itself** (post-PoC): persistent connection, FIFO pairing, 30 s timeout,
64 MiB line cap, ≤10 in-flight, 10k row cap; a permanent live-mutation banner plus confirm
dialogs for `EVICT`/`ALTER SYSTEM`/mutating statements.

## Testing strategy

- Each phase ships with unit tests mirroring the extension's contract tests (advise
  extractor, system-metrics accumulator, pattern fixtures) and, where feasible,
  instrumented UI tests on the `tabletApi34` managed device and macOS unit/UI tests for the
  SwiftUI equivalents.
- Both platforms must keep `./gradlew check` / the full `EdgeStudioUnitTests` suite green
  per phase.

## Review resolutions (2026-08-24)

1. **Metrics default ON.** "Collect system metrics" defaults to on; the toggle's subtitle
   says it applies at next database open.
2. **Debug Console is a PoC, own-instance only.** We build the console only for the embedded
   Ditto we control; no generic socket-path UX. Two spikes (Network.framework on macOS,
   `LocalSocket` filesystem namespace on Android) must pass before UI work starts.
3. **SwiftUI home: App Metrics** segmented sub-tab; **Android home: Database Metrics** filter
   chips + card grid; both share the summary-cards-plus-table content shape outlined above.

## Ordering

Phase 1 (patterns) can land immediately. Phase 2 (ADVISE) next — it's pure host-side code.
Phase 3 (system:metrics) needs the pre-open env hook built first. Phase 4 (Debug Console)
last and gated on the two PoC spikes per platform.
